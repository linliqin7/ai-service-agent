# 需求发现与价值验证方法

## 1. 需求不是功能，而是待验证的因果链

不要从“做一个 AI 客服”开始。需求分析要回答：谁在什么场景下，想完成什么任务；当前方案在哪一步失败；失败造成什么可观察损失；为什么现有方案不足；我们的方案准备验证什么假设。

```text
业务目标 → 角色 → 用户任务 → 当前流程 → 障碍/根因 → 损失 → 机会假设 → 方案 → 指标
```

“用户需要客服”不是需求；“开户高峰时，用户反复询问相同材料，人工坐席需要重复解释，造成排队和坐席占用；如果标准问题由带版本的知识链路自动处理，可能减少重复人工会话”才是可以验证的需求假设。

## 2. 三类证据

### 业务证据

证明机构是否真的有问题和投入动机：年报、官方数字化材料、客服/运营招聘、采购案例、帮助中心和服务流程。它能支持“问题存在”和“组织关心”，不能直接证明方案能降低成本。

### 用户证据

证明问题是否高频、困难且影响任务完成：App 评论、客服 FAQ、实际任务走查、访谈、公开投诉。必须把“体验不好”拆成任务、失败点、耗时、重复次数、转人工和后果。

### 方案证据

证明为什么需要 Agent：哪些问题 FAQ 能解决，哪些问题需要用户实时数据，哪些问题需要多轮澄清、工具组合或风险判断。只有方案证据成立，才有理由使用 Agent，而不是普通搜索或规则页面。

## 3. 价值判断框架

每个候选需求按五项打分，不用主观印象直接排序：

- 频率：用户出现得多不多；
- 任务价值：解决后是否真正完成一个业务任务；
- 当前损失：等待、转人工、投诉、错误、流失或运营成本；
- Agent 适配度：是否需要语义理解、上下文、实时数据或工具组合；
- 风险可控性：错误是否可拦截、审计和转人工。

优先做“高频/高任务价值/Agent 适配度高/风险可控”的问题。高风险但无法安全自动处理的问题，不是删掉，而是定义为拒答或转人工场景。

## 4. 竞品调研不比较 Logo，而比较任务完成链路

每个竞品用同一组任务测试：规则查询、个人资格判断、开户进度、订单诊断、模糊追问、高风险投资请求。记录入口、是否登录、是否澄清、是否查个人数据、是否给依据、是否完成任务、是否给下一步、是否转人工、是否可追溯。

竞品分四层：直接金融 B 端方案、券商/银行 App 场景产品、能力标杆、人工/FAQ/电话等替代方案。宣传页只能说明“声称具备什么”，不能证明真实体验；结论必须标记证据等级。

## 5. 证据等级

- A：监管机构、交易所、券商官方文件或实际操作记录；
- B：官方帮助文档、产品说明、公开流程；
- C：App 评论、媒体报道、案例文章；
- D：个人推测或待验证设计假设。

任何“能降低人工率”“能减少流失”“用户最常问某问题”的结论，都必须有来源或明确标为假设。
