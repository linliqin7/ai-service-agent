# Historical Interview Narrative and Follow-up Notes

> This interview note predates the public v1.0 product alignment. It remains useful for historical implementation discussion, but the current product narrative, scope, and evaluation results are defined by the root [PRD](../PRD.md), [README](../README.md), and [v1.0 Architecture Overview](architecture/overview-v1.0.md).

## 60 秒项目开场

“我做的是一个面向券商经纪业务的个人智能客服项目，付费方假设是券商，使用方是个人投资者。立项动机来自我对客服项目的接触，以及金融业务辅导给出的场景线索；我没有券商内部日志，所以没有虚构需求量或成本改善数字。

我把问题分成规则解释、个人状态、异常诊断和高风险请求。模型实际连接 DeepSeek，但身份绑定、工具白名单、订单归属和事实依据都由程序控制。用户可以先问一个模糊问题，经过澄清和模拟登录，再查询工具并得到可追踪的结果。

目前实现并测试了完整 Web 流程、两个维度的用户画像、版本化知识、模型 Loop、工单和评测。真实模型调用与接口编排已经跑通，业务数据是模拟的；我重点想说明的是如何做产品边界、控制失败成本，以及用 Bad Case 改进系统。”

## 五分钟讲述顺序

### 0:00–0:45：为什么是这个任务

说明真实动机，不把它包装成已验证的市场结论。比较候选：纯问答可用 FAQ；个人状态必须有数据权限；复杂诊断需要动态选择信息。经纪客服有这些任务差异，适合做能力验证。

补充：“传统 NLP 并非只能关键词匹配，我没有把它简单当成落后对手；要证明 LLM 的增量价值，应与现有客服流程做同样本对照。”

### 0:45–1:20：用户与范围

券商是购买和治理系统的人，散户是使用者；人工坐席承接复杂问题，合规部门负责规则审批。资产层级与生命周期两个维度描述不同服务上下文，风险测评独立判断。第一期做客服，不做主动营销或投资建议。

### 1:20–2:20：演示三条链路

先演示投资建议拒答，再演示开户材料问答，最后演示订单多轮查询。点击处理记录说明：模型不是只生成文字，而是选择工具；工具执行器绑定账户，越权订单不能进入模型上下文。

补充资格例子：“我能不能开创业板”先登录，再取画像与演示规则，代码逐项比较。演示门槛不代表最新监管规则，最终开通还要券商完整审核。

### 2:20–3:15：架构取舍

采用 Router + Workflow + 局部 Agent Loop。固定规则用固定流程；模型根据观察选择工具，但有白名单、Schema、重复动作和预算限制。模块拥有不同职责，并不意味着都应该做成独立 Agent。

规则知识当前用可解释的词项检索，规模较小，没有冒充已实现向量混合检索。DeepSeek 可以选择回答所需的完整依据句；账户事实确定性输出。这是金融场景下对自由生成能力的主动约束。

### 3:15–4:15：讲一个真正发生的 Bad Case

选择“开户进度被当成材料问答”或“有效引用仍能输出投资建议”。说清输入、错误行为、根因、修复位置、验证证据和代价。不要只说“优化 Prompt 后提升了准确率”。

### 4:15–5:00：评测与局限

报实际样本数与分母：49 条主集、18 条留出合成样本，另有真实模型四条链路烟测，以及程序与浏览器测试。强调离线契约断言不是专家合规评级，也不是线上 FCR。

如果落地，需要真实客服日志、审核后的监管和券商知识、生产身份认证、券商接口、坐席流程和专业合规验收。这些没有完成，不能在面试中说成已上线。

## 必练追问

**为什么不用五个并行 Agent？**

工具、检索、生成、检查是能力模块。把它们都赋予独立决策权会增加延迟、协调成本和审计复杂度。只有需要根据观察调整后续行动的部分才保留模型规划。多 Agent 是可选工程方案，不是项目含金量的指标。

**Agent Loop 与固定 Workflow 的界线是什么？**

固定流程由代码预先指定下一步；Loop 中模型读取当前观察并选择下一动作。我的无密钥模式是固定序列，有密钥时由模型选择白名单工具与停止动作，二者会在 trace 中区分。

**FAQ、RAG、工具怎么分？**

审核过且问题稳定的 FAQ 直接回答；规则知识从有版本的资料中检索；个人状态必须查询账户工具。不能因为“开户”这个词检索到了内容，就认为用户只问开户常识。

**你真的做了向量 RAG 吗？**

没有。实际实现是元数据治理、受控同义改写、关键词和中文词项排序、引用以及失败处理。下一步会在真实语料上比较词法与向量召回，不会把规划说成实现。

**有引用就安全吗？**

不安全。我实际构造过“合法引用 + 无依据建议”的反例。目前选择完整依据句并验证，减少自由生成风险。即使这样，原文专业正确性与政策完整性还需要专业审核。

**为什么不是所有问题都调用模型？**

简单 FAQ 没必要付出模型延迟和不确定性；身份与权限更不应该由模型决定。模型的价值在语义理解和受控动态规划，工具事实和确定规则留给可验证代码。

**工具失败怎么办？**

不把异常当作业务事实，不猜订单状态。短暂模型错误有限重试；数据错误、越权、非法动作、重复调用或依据缺失停止并进入本地工单。真实坐席还未接入，所以界面明确不会有人接单。

**没有真实业务数据，项目价值在哪里？**

可以验证流程、权限、失败路径、工具契约与评测机制；不能验证真实问题分布、ROI、规模性能和生产合规。我把能验证与不能验证的结论分开。

**北极星指标是什么？**

合规前提下的一次解决率，分母是有明确可核验目标的有效客服会话；分子还要同时满足任务完成、事实正确和合规。仅降低转人工可能通过错误强答达成，所以它不能单独作为目标。

**如何验证商业价值？**

取真实任务量、峰值排队、各问题人工耗时与失败成本；对照 FAQ/原系统/普通 LLM/受控 Agent，比较同样本的安全完成率、转人工、成本与客户体验。投诉和财产安全类问题不应为降低人工率而被强行自动化。

**合规规则由谁维护？**

真实机构应由业务与合规共同负责解释和审批，研发负责可执行规则、版本、生效区间和回归。这个个人项目的演示审核不是金融机构合规批准。

**用户资产高就可以推荐高风险产品吗？**

不可以。资产与生命周期只是服务画像，风险测评和适当性是独立约束。客服第一期没有产品推荐能力，也不能把有钱等同于能承担某种风险。

## 自我介绍与事实边界

当前资料不足以确认你的学校、实习职责和个人贡献，不能替你编造一篇“真实履历”自我介绍。自我介绍可以按“真实背景→你实际负责的客服工作→如何迁移到金融项目→最想被追问的 Bad Case”组织，具体经历等你核实后再填写。

准确措辞：

- “我实际参与过的实习工作是……”——仅使用你能提供细节和证据的经历。
- “在这个个人项目中，我和 AI 编程工具协作实现并验证了……”——明确工具协作，不虚报独立手写代码。
- “如果进入真实券商环境，我会补充……”——这是落地方案，不是已取得的结果。

禁止说：真实客户成本降低多少、监管知识全覆盖、已完成生产级鉴权、真实坐席接管、所有问题都能答、已经上线券商。这些都没有证据。
