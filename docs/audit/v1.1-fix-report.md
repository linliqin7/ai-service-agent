## 2. Case 1 Fix

### Root cause

`app/runtime/router.py` 先用“未成交/没成交”等通用词命中订单意图，再判断 `public_definition()`，导致“未成交是什么意思？”被当作个人订单诊断。

### Implementation

- 将公共定义判断放到通用订单关键词判断之前。
- 扩展公共定义表达：`什么是`、`怎么理解`、`定义`、`代表什么` 等。
- 扩展个人上下文排除：`我的订单`、`我的委托`、`这笔`、`那笔`、`订单号`、`订单状态` 等。
- 没有删除“未成交”订单关键词，因此带有个人/订单上下文的诊断路径仍可进入 `order`。

### Why this fix is generalizable

规则按用户任务表达和个人上下文划分，而不是针对“未成交是什么意思？”做字符串特判。公共定义问题优先进入知识路径；个人订单上下文仍保留订单路由。

### Tests

- `test_public_unfilled_definition_does_not_enter_private_order_flow`：PASS
- 既有订单澄清、订单号解析、归属校验测试：PASS

## 3. Case 2 Fix

### Root cause

unknown 分支把 `clarifications` 写入 `SessionState.pending_slots`，但成功的公共知识回答没有清理该短期状态，导致下一次 unknown 直接进入 handoff。

### Implementation

在 `app/runtime/engine.py` 增加 `reset_pending_task_context()`，明确清理 `pending_slots` 中的短期任务上下文；身份、消息历史和 trace 不在 `pending_slots` 中，不受影响。

在以下任务结束点调用清理：

- 风险拒答
- 明确人工转接
- 成功私有任务
- 成功知识回答
- 模型分类后的拒答/转接

登录续办仍先读取 pending query，再在任务完成后清理，因此没有改变“登录后继续查询”流程。

### State lifecycle

- unknown：`clarifications=1`
- 成功知识回答：清除旧任务上下文
- 新 unknown：重新从 `clarifications=1` 开始，不直接 handoff

### Tests

- `test_successful_answer_resets_stale_clarification_context`：PASS
- 既有 runtime、integration、order clarification 和 API session 测试：PASS

## 4. Case 3 Fix

### Root cause

`search_knowledge` 的结果被放入 `_diagnose()` 的 `observations`，但 `render_facts()` 只读取业务事实工具，最终 response 没有 citations，也没有使用检索事实。

### Evidence chain

当前链路为：

`search_knowledge observation → knowledge_citations() → render_facts() 的知识依据 → response.citations`

### Implementation

在 `app/runtime/tools.py`：

- 增加 `knowledge_citations()`，只提取实际由 `search_knowledge` 返回的、去重后的知识记录。
- `render_facts()` 在保留账户/订单事实优先级的基础上，追加真实知识记录文本作为“知识依据”。

在 `app/runtime/engine.py`：

- 私有任务成功完成后，从 observations 提取知识 citations 写入 response citations。
- 没有结果时保持原有事实回答行为。
- 没有硬编码测试知识 ID，也没有把整个知识库塞入回答。

### Tests

- `test_agent_search_knowledge_observation_reaches_final_evidence`：PASS
- 既有 fake planner、工具白名单、无证据回答、知识引用和安全策略测试：PASS

## 5. Case 4 Fix

### Root cause

`app/api.py` 的 `/api/knowledge` 直接返回 `records()`，绕过了 retriever 使用的治理规则。

### Governance reuse

接口现在复用 `app/rag/governance.py` 的 `current(record, audience='public')`，统一检查：

- 生效/失效日期
- `demo_reviewed` 或 `approved` 状态
- `public` audience
- `direct_answer=True`

没有在 API 层复制治理逻辑，也没有修改正式知识 fixture 或 retriever。

### Tests

- `test_public_knowledge_api_filters_non_public_records`：PASS
- 既有 RAG 过期、draft、staff、inactive 过滤测试：PASS

## 8. Architecture Impact

本次是局部行为修复，没有引入新的 Agent 框架、模型、向量数据库、Reranker 或 Multi-Agent。架构影响限于：

- Router：公共定义优先于通用订单关键词。
- Session：短期任务槽位在任务完成时清理。
- Evidence：工具检索结果进入事实渲染和 citations。
- Knowledge API：公开浏览出口复用现有治理函数。

现有的确定性路由、受控工具执行、账户归属校验、RAG 检索、风险拒答、人工转接和本地存储能力均保留。

## 9. Remaining Limitations

- 测试仍使用模拟账户、模拟订单和本地知识 fixture，不能证明真实券商系统行为。
- 没有验证真实 LLM planner 在网络环境下的所有输出变体。
- `search_knowledge` 的证据合并是确定性文本依据，不是完整的多文档冲突解决系统。
- 依赖弃用警告仍存在，本阶段未升级依赖。
- 本阶段未做生产部署、并发、延迟或浏览器 E2E 验证。

## 10. V2 Candidates

以下仅记录未来工作，本阶段未实现：

本阶段没有新增依赖，没有修改产品定位，也没有扩大 Agent 架构范围。
