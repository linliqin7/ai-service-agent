# 业务覆盖与事实边界

“全生命周期覆盖”指问题有可解释的处理出口；不声称任意问题都能自动完成，也不声称拥有所有监管知识。

| 业务域 | 现有处理能力 | 未接入时的出口 |
|---|---|---|
| 开户/身份认证 | 材料说明、本人模拟申请状态 | 特殊主体、真实审核联系官方 |
| KYC/风险测评 | 通用说明、本人等级与有效状态 | 不指导用户修改答案以过审 |
| 权限/适当性 | 创业板/科创板/北交所演示逐项比对 | 最新门槛与完整条件待官方核验 |
| 委托/成交/撤单 | 订单号澄清、状态、原因码、归属检查 | 不执行撤单，不推断缺失行情原因 |
| 资金/银证/出入金 | 本人模拟可用/可取/冻结金额 | 无流水和银行回执时不判具体原因 |
| 账户维护 | 状态、证件待更新、资料维护说明 | 变更、销户、转托管在官方流程完成 |
| 持仓/资产 | 模拟持仓、资产查询和成本口径说明 | 不把模拟估值当实时行情 |
| 清算/交收 | 说明不同市场和产品口径 | 不无依据承诺资金何时可取 |
| 行情/公告/分红 | 明确数据未接入，提供官方查询方向 | 不生成最新价格或公告结论 |
| 基金/费用/赎回 | 客观说明需核对说明书与渠道 | 无产品资料时不确定费率及确认日 |
| 新股申购/中签 | 解释核查路径 | 无额度接口时不猜个人资格或结果 |
| 客诉/申诉 | 创建、保存、查看本地交接摘要 | 没有真实坐席、不会实际处理投诉 |
| 安全/隐私 | 密码找回说明、敏感信息脱敏、越权阻断 | 挂失、冻结、报警需官方渠道 |
| 无法识别 | 一次澄清，持续不明则人工出口 | 不用模型常识补造业务事实 |

## 画像的两个维度

资产层级用于说明服务上下文；生命周期用于识别开户、入金后、交易中、维护中的差异。两者是正交的业务维度，不代表真实客户分布。风险测评是第三项独立适当性信息，不能用资产高低替代。

当前画像不触发主动营销，不做产品推荐。长期金融助手路线可以在获得适当性规则、产品目录、资质和责任边界后单独设计，不能悄悄混入客服一期。

## 事实证据等级

- 已实测：本地 HTTP 服务、DeepSeek 响应、工具执行、SQLite 存储、浏览器交互、离线程序断言。
- 演示数据：四个账户、三笔订单、14 条服务说明、三组资格测试规则。
- 研究假设：真实客户需求频次、坐席成本、一次解决率、留存影响。
- 尚未核验：当前全量监管数字、券商具体办理口径、产品最新费率。

现有研究来源日志明确仅核验部分官方入口。未将这些入口伪装成具体规则的条文证据。项目内“演示审核”由开发者为案例整理，不代表券商合规部门批准。

## 为什么做这个项目

真实动机可以如实说明：过去接触过智能客服，希望迁移任务拆解和评测经验；金融业务辅导提供了问题线索。进一步选择经纪客服，是因为这里同时需要静态规则、本人状态、诊断工具和合规处理，适合验证这些产品能力。

这能解释“为何选择这个能力验证项目”，不能证明已经发现有付费价值的市场。商业验证仍需券商客服日志、访谈、任务量和单次服务成本，比较现有 FAQ、人工、普通 LLM 与受控 Agent 的增量收益。

更准确的产品判断是：先验证可控完成有业务差异的任务，再用真实数据判断投入优先级；不以“传统 NLP 只能关键词匹配”作为立项事实。传统客服同样可以使用语义分类、检索和 API 编排，LLM 的收益需要对照验证。
